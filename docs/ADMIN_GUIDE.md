# Руководство администратора ИС «ГрузПоток»

Документ предназначен для пользователей с ролями «Администратор»
и «Диспетчер». Порядок развёртывания изложен в [DEPLOY.md](DEPLOY.md).

---

## 1. Панель администратора

Доступна по адресу `/console/`. Разделы делятся на две группы: работа
с данными открыта с роли «Диспетчер», ведение системы — только
администратору. Перечень вкладок собирается по роли, поэтому показанное
и доступное совпадают.

| Раздел | Назначение | Наименьшая роль |
|---|---|---|
| Обзор системы | Состояние данных, загрузок и учётных записей | Диспетчер |
| Загрузка данных | Реестр источников, регламент, запуск, журнал | Диспетчер |
| Карантин | Записи источников, не прошедшие проверку качества | Диспетчер |
| Осмотр реестра | Подтверждение записей реестра человеком | Диспетчер |
| Качество данных | Автоматические проверки полноты | Диспетчер |
| Пользователи | Учётные записи, назначение ролей, блокировка | Администратор |
| Справочники | Округа, типы объектов, категории грузов, источники | Администратор |
| Обращения | Обработка сообщений обратной связи | Администратор |
| Материалы | Публикация аналитических обзоров | Администратор |
| Журнал аудита | Действия всех пользователей | Администратор |
| Состояние среды | Версии компонентов, объёмы, обслуживание | Администратор |

Помимо собственной панели сохранена штатная административная панель Django
по адресу `/django-admin/` — она применяется для низкоуровневых операций со
справочниками с контролем ссылочной целостности.

## 2. Управление пользователями

### 2.1. Назначение роли

Раздел «Пользователи» содержит перечень учётных записей с отбором по роли,
состоянию и поисковому запросу. Роль изменяется выбором значения в списке и
нажатием «Применить».

Модель полномочий вложенная: каждая последующая роль включает права всех
предыдущих.

| Роль | Полномочия |
|---|---|
| Наблюдатель | Просмотр реестров, карты, аналитики; избранное; сохранённые виды |
| Аналитик | Дополнительно: выгрузка отчётов, конструктор сравнений, токен API |
| Диспетчер | Дополнительно: загрузка данных, карантин, осмотр реестра, качество |
| Администратор | Полный доступ, включая ведение системы |

Изменение роли фиксируется в журнале аудита.

### 2.2. Блокировка учётной записи

Кнопка «Заблокировать» лишает пользователя возможности входа, сохраняя все
связанные записи — избранное, сохранённые виды, историю выгрузок.
Разблокировка восстанавливает доступ.

**Ограничение.** Заблокировать собственную учётную запись либо изменить
собственную роль невозможно. Ограничение введено намеренно: при единственном
администраторе такое действие привело бы к полной потере управления системой.

### 2.3. Восстановление доступа администратора

Если все административные учётные записи оказались заблокированы,
восстановление выполняется из командной строки сервера:

```bash
python backend/manage.py shell -c "
from django.contrib.auth.models import User
from accounts.models import profile_for, Role
u = User.objects.get(username='admin')
u.is_active = True; u.save()
p = profile_for(u); p.role = Role.ADMIN; p.save()
"
```

## 3. Ведение справочников

Раздел «Справочники» отображает состав четырёх классификаторов с указанием
числа связанных записей. Изменение выполняется через штатную административную
панель.

**Правила изменения.**

- Удаление записи, на которую есть ссылки, блокируется на уровне базы данных.
- Изменение наименования отражается во всех разделах немедленно.
- Изменение машинного кода вступает в силу только после повторной загрузки
  данных: код используется при сопоставлении записей из внешних источников.

### 3.1. Координаты центров округов

Если у округа отсутствуют координаты центра, он не получает подписи на карте.
Заполнение выполняется командой:

```bash
python backend/manage.py district_centers
```

Команда идемпотентна. Ключ `--force` перезаписывает уже заполненные значения
эталонными.

## 4. Обработка обращений

Раздел «Обращения» содержит сообщения из формы обратной связи с отбором по
состоянию и теме.

### 4.1. Состояния обращения

| Состояние | Значение |
|---|---|
| Новое | Не рассмотрено |
| В работе | Принято к рассмотрению |
| Отвечено | Ответ направлен заявителю |
| Закрыто | Закрыто без ответа |

### 4.2. Порядок работы

1. Откройте обращение из перечня.
2. Нажмите «Взять в работу», если требуется время на рассмотрение.
3. Введите текст ответа и нажмите «Отправить ответ».

Ответ направляется на указанный заявителем адрес; состояние меняется на
«Отвечено» с указанием обработавшего и времени.

Обращения, не относящиеся к системе, закрываются без ответа кнопкой
«Закрыть без ответа».

### 4.3. Рекомендации по обработке

Замечания к данным передавайте поставщику соответствующего источника —
сведения об источнике каждой записи доступны в её карточке. Предложения по
развитию включайте в план доработок. Запросы доступа удовлетворяйте после
проверки принадлежности заявителя к указанной организации.

## 5. Контроль качества данных

Раздел «Качество данных» выполняет семь автоматических проверок при каждом
открытии.

| Проверка | Следствие дефекта |
|---|---|
| Объекты без координат | Не отображаются на карте, не участвуют в поиске ближайших |
| Объекты без указания мощности | Не учитываются в расчёте обеспеченности округа |
| Объекты без адреса | Затруднена идентификация объекта пользователем |
| Участки сети без геометрии | Не отображаются на слое дорожной сети |
| Инциденты без привязки к участку | Не попадают в статистику по округам |
| Незакрытые инциденты старше 30 суток | Вероятно, отсутствует отметка об устранении |
| Записи без указания источника | Невозможно проследить происхождение сведений |

**Трактовка результатов.** Ненулевое число замечаний не свидетельствует о
неисправности системы. Пропуски отражают состояние исходных источников: часть
сведений поступает в неполном виде и уточняется при последующих загрузках.

Устранение выполняется либо на стороне поставщика данных — через запрос на
уточнение, — либо ручным дополнением через административную панель.

Перечень проверок составлен по принципу «дефект, искажающий выводы»: в него
включены только те условия, наличие которых меняет результат агрегации или
делает запись недоступной пользователю.

## 6. Загрузка данных

### 6.1. Реестр источников

Раздел «Загрузка данных» открывается составом наборов: обозначение конвейера,
наполняемая таблица, число проверок качества, регламент обновления и итог
последней загрузки. Набор, у которого подошёл срок обновления, помечается
отдельно.

| Набор | Что загружает | Регламент |
|---|---|---|
| `osm.districts` | Границы административных округов | еженедельно |
| `osm.objects` | Реестр объектов логистической инфраструктуры | еженедельно |
| `osm.roads` | Магистральная улично-дорожная сеть | еженедельно |
| `osm.zones` | Зоны ограничения движения грузового транспорта | ежемесячно |
| `osm.corridors` | Федеральные грузовые коридоры | ежемесячно |
| `osm.roadworks` | Участки, закрытые на реконструкцию | ежедневно |
| `reference.frame` | Магистрали грузового каркаса | ежеквартально |
| `rosstat.freight` | Ряды перевозок и грузооборота | ежеквартально |
| `upload.flows` | Ряд, присланный файлом | по присылке |

Порядок наборов в реестре значим: объект относится к округу по координатам,
зона строится по геометрии кольцевой магистрали, принадлежность каркасу
отмечается в уже заполненном реестре магистралей. При запуске нескольких
наборов этот порядок соблюдается независимо от порядка выбора.

### 6.2. Запуск загрузки

Форма «Запуск загрузки» принимает набор данных и два условия.

| Условие | Когда применять |
|---|---|
| Обратиться к источнику заново | Требуется свежая выгрузка. Без отметки используется сохранённый ответ службы |
| Привести реестр к составу источника | Требуется удалить записи, которых в источнике больше нет |

При настроенном `FF_CELERY_BROKER_URL` задача передаётся исполнителю: страница
отвечает сразу, итог появляется в журнале по завершении. Без очереди загрузка
выполняется в том же процессе, и страница ответит после её окончания —
обращение к внешней службе может занять минуты.

Те же наборы запускаются из командной строки:

```bash
python backend/manage.py etl --list                  # состав реестра
python backend/manage.py etl --all                   # все наборы по порядку
python backend/manage.py etl osm.objects --prune     # привести реестр к источнику
python backend/manage.py etl --all --refresh         # обратиться к службам заново
python backend/manage.py etl --all --offline         # только по сохранённым ответам
python backend/manage.py etl --all --dry-run         # проход без записи
python backend/manage.py etl --due                   # то, что подошло по регламенту
```

### 6.3. Чтение журнала

Каждая загрузка оставляет запись со счётчиками: создано, обновлено, без
изменений, отклонено, удалено. Соотношение между ними и есть содержание записи.

| Что видно | Как читать |
|---|---|
| Почти всё «без изменений» | Обычное состояние повторного запуска: источник не менялся |
| Много «создано» вне первой загрузки | Источник существенно пополнился либо изменился ключ записи |
| Ненулевое «отклонено» | Часть записей не прошла проверки; причины — в карантине |
| Итог «ошибка» | Загрузка прервана; причина указана в карточке |

Карточка загрузки открывается по времени начала в журнале и показывает
параметры запуска, кто его начал и перечень отклонённых записей.

### 6.4. Карантин

Раздел «Карантин» содержит записи источников, не прошедшие проверку качества.
Для каждой сохранены код проверки, формулировка причины, положение в источнике
и исходное содержимое.

Порядок работы:

1. откройте сводку причин и определите, какая проверка срабатывает чаще всего;
2. по положению в источнике найдите запись — элемент разметки либо строку
   присланного файла;
3. исправьте сведения на стороне источника;
4. отметьте разобранные записи — они уйдут из очереди, оставшись доступными
   для сверки.

Запись, уже стоящая в очереди по той же проверке, повторно не откладывается:
регламентная загрузка идёт по расписанию, и неисправленный источник иначе
удлинил бы очередь копиями одного и того же.

Доля отклонений характеризует состояние источника, а не работу системы.
Элементы выгрузки, не относящиеся к предметной области, в карантин не
попадают — их отсев виден в сводке загрузки отдельным счётчиком.

### 6.5. Осмотр записей реестра

Реестр наполняется размеченными сведениями, и полнота их неодинакова:
наименование указано у восьмой части записей, адрес — у половины. Осмотр
отвечает на вопрос, соответствует ли запись действительности.

Раздел «Осмотр реестра» показывает очередь, начиная с записей, о которых
источник сообщает меньше всего: объект без наименования и адреса труднее
опознать на местности. По каждой записи доступны три действия:

| Действие | Когда применяется |
|---|---|
| Подтвердить | Запись соответствует действительности |
| Требует уточнения | Обнаружено расхождение; замечание обязательно |
| Снять отметку | Прежний осмотр более не действителен |

Осмотр не правит сведения источника: разметка OpenStreetMap исправляется
в самой разметке, иначе правка была бы стёрта следующей загрузкой,
а величина потеряла бы прослеживаемость. Итог осмотра виден на карточке
объекта и выгружается вместе с реестром.

Выгрузка, пришедшая после осмотра, помечает его устаревшим: подтверждение
относилось к прежнему состоянию записи. Такие записи отбираются в разделе
отдельно.

### 6.6. Приём выгрузки от пользователя

Раздел «Загрузить файл» принимает ряд перевозок в виде файла CSV либо книги
Excel. Ожидаемый состав колонок приведён на самой странице, там же отдаётся
образец для заполнения.

Строки проходят те же проверки, что и данные внешних служб. Не прошедшие
откладываются в карантин с номером строки в присланном файле. Повторная
присылка того же ряда обновляет записи, а не удваивает их.

### 6.7. Регламентное обновление

Периодичность объявляет сам набор данных; срок отсчитывается от последней
успешной загрузки, поэтому неудачная попытка его не сдвигает.

**С очередью задач.** Планировщик Celery ведёт расписание, собранное
из реестра наборов; исполнитель работает в один поток — одновременное
обращение нескольких загрузок к общедоступной службе приводит к отказу
по превышению квоты.

**Без очереди.** Регламент ведёт системный таймер
`deploy/freightflow-etl.timer`: ежечасно он вызывает `manage.py etl --due`,
а решение о том, что пора обновлять, принимается по журналу.

### 6.8. Сброс кеша

Агрегированные сводки кешируются на пять минут. Запуск загрузки из панели
сбрасывает кеш сам; после правки данных иным способом воспользуйтесь кнопкой
«Сбросить кеш» в разделах «Обзор системы», «Загрузка данных» или «Состояние
среды».

## 7. Журнал аудита

Раздел «Журнал аудита» фиксирует значимые события системы.

| Тип действия | Что записывается |
|---|---|
| Вход | Успешная авторизация с указанием адреса подключения |
| Изменение | Правка данных предметной области |
| Выгрузка | Формирование отчёта с указанием набора и формата |
| Административное | Изменение роли, блокировка учётной записи |

Обращения к страницам просмотра в журнал не записываются: их объём сделал бы
журнал непригодным для разбора инцидентов.

Отбор доступен по типу действия, пользователю и периоду. Каждая запись
содержит идентификатор запроса, совпадающий с выводимым в подвале страницы, —
это позволяет сопоставить обращение пользователя с записью в журнале сервера.

## 8. Публикация материалов

Раздел «Материалы» управляет аналитическими обзорами портала.

| Действие | Результат |
|---|---|
| Опубликовать | Материал становится доступен в публичном разделе |
| Снять | Материал скрывается, оставаясь в системе |
| На главную | Материал выносится в блок главного материала |

Создание и правка текстов выполняются через штатную административную панель
(`/django-admin/content/article/`).

## 9. Наблюдение за системой

### 9.1. Состояние среды

Раздел «Состояние среды» отображает версии компонентов, тип и объём базы
данных, режим отладки, параметры кеша и каталога выгрузок.

**Обратите внимание.** Значение «Режим отладки: включён» в промышленном
контуре недопустимо — оно раскрывает подробности внутреннего устройства при
возникновении ошибок. Установите `FF_DEBUG=False` и перезапустите службу.

### 9.2. Проверка доступности

Конечная точка `/healthz` возвращает состояние соединения с базой и объёмы
ключевых таблиц. Предназначена для системы мониторинга.

### 9.3. Регламентные операции

| Операция | Периодичность | Способ |
|---|---|---|
| Обновление данных | По регламенту набора | Планировщик Celery либо таймер `freightflow-etl.timer` |
| Разбор карантина | Еженедельно | Раздел «Карантин» |
| Резервное копирование | Ежесуточно | `deploy/backup.sh` по расписанию |
| Очистка выгрузок | Ежесуточно | Системный таймер `freightflow-cleanup.timer` |
| Проверка качества данных | Еженедельно | Раздел «Качество данных» |
| Разбор журнала аудита | Еженедельно | Раздел «Журнал аудита» |
| Обновление версии | По мере выпуска | См. [DEPLOY.md](DEPLOY.md) |

## 10. Типовые ситуации

### Пользователь сообщает об ошибке на странице

1. Запросите идентификатор запроса из подвала страницы.
2. Найдите соответствующую запись в журнале сервера:
   ```bash
   grep "<идентификатор>" /opt/freightflow/logs/freightflow.log
   ```
3. Запись содержит полный контекст обращения, включая параметры и трассировку.

### Показатели отображаются устаревшими

Сбросьте кеш через раздел «Состояние среды». Если расхождение сохраняется —
проверьте журнал загрузок: возможно, регламентное обновление не выполняется.

### Раздел загружается медленно

Проверьте объём таблиц в разделе «Обзор системы». При объёме свыше 500 000
записей в таблице замеров обстановки рассмотрите архивирование наблюдений
старше года.

### Место на диске заканчивается

Основные потребители — каталог выгрузок и журналы. Выполните очистку:

```bash
python backend/manage.py cleanup_exports --days 7
```

Проверьте настройку ротации журналов; при её отсутствии добавьте правило в
`logrotate`.
