## 1. Назначение документа

Документ определяет объём, методы, критерии и порядок проведения испытаний
информационной системы «ГрузПоток». План распространяется на функциональные
и нефункциональные характеристики системы и служит основанием для приёмки
результатов разработки.

---

## 2. Объект испытаний

Веб-приложение на платформе Django, включающее:

- одиннадцать таблиц предметной области с пространственной привязкой;
- десять публичных разделов с реестрами, картой и аналитикой;
- личный кабинет из десяти разделов;
- панель администратора из девяти разделов;
- программный интерфейс REST из восемнадцати конечных точек;
- подсистему формирования отчётов в пяти форматах;
- четыре роли с вложенной моделью полномочий.

**Контуры испытаний:**

| Контур | СУБД | Назначение |
|---|---|---|
| Разработки | SQLite 3.45 | Быстрый прогон, отладка |
| Промышленный | PostgreSQL 16 + PostGIS 3.4 | Приёмочные испытания |

---

## 3. Область испытаний

### 3.1. Входит в область

| Раздел | Проверяемые характеристики |
|---|---|
| Пространственный слой | Разбор и формирование геометрии, метрики, запросы к обеим СУБД |
| Модель данных | Ограничения целостности, производные характеристики, выборки |
| Агрегация | Корректность сводок, работа кеша |
| Аналитика | Нормирование, кластеризация, регрессия, прогноз, сценарии |
| Веб-интерфейс | Отклик страниц, отбор, сортировка, постраничный вывод, формы |
| Разграничение доступа | Полномочия ролей, журнал аудита, токены доступа |
| Программный интерфейс | Структура ответов, параметры отбора, спецификация |
| Формирование отчётов | Корректность файлов пяти форматов |
| Процедуры загрузки | Разбор SQL, идемпотентность, ссылочная целостность |
| Адаптивность | Отображение при ширине экрана 360–1920 пикселей |
| Интернационализация | Полнота перевода интерфейса на английский язык |
| Кроссбраузерность | Chrome, Firefox, Edge, Safari |
| Устойчивость под нагрузкой | Время отклика при 50 одновременных пользователях |

### 3.2. Не входит в область

- испытания на проникновение и аудит защищённости инфраструктуры;
- испытания при объёме данных свыше 500 000 записей;
- проверка отображения в браузерах Internet Explorer и Opera Mini;
- нагрузочные испытания продолжительностью свыше одного часа;
- проверка достоверности исходных данных внешних источников (система
  отвечает за корректность обработки, но не за качество поступающих сведений).

## 4. Методы испытаний

Применяются шесть методов; для каждого указаны цель, инструмент и объём.

### 4.1. Модульное тестирование

**Цель:** проверка корректности отдельных функций и производных характеристик
в изоляции от остальной системы.

**Инструмент:** pytest.

**Объём:** геометрический слой (35 проверок), доменные модели (36 проверок),
расчётные функции аналитики (17 проверок).

**Особенность:** проверяются не только штатные случаи, но и вырожденные —
пустой ряд, ряд из одинаковых значений, единственное наблюдение,
некорректный ввод.

### 4.2. Интеграционное тестирование

**Цель:** проверка взаимодействия слоёв — агрегатов, обращающихся к базе,
процедур загрузки и формирования файлов.

**Инструмент:** pytest с приспособлениями базы данных (pytest-django).

**Объём:** агрегированные выборки (22 проверки), команды управления
(28 проверок), формирование отчётов (45 проверок), аналитика с обращением к
базе (25 проверок).

### 4.3. Функциональное тестирование

**Цель:** проверка поведения системы с точки зрения пользователя — отклик
страниц, действие условий отбора, обработка форм.

**Инструмент:** тестовый клиент Django, ручные проверки по тест-кейсам.

**Объём:** 68 автоматических проверок, 54 тест-кейса для ручного выполнения.

### 4.4. Тестирование разграничения доступа

**Цель:** подтверждение того, что ограничения реализованы на уровне
представлений, а не скрытием элементов интерфейса.

**Инструмент:** тестовый клиент Django.

**Объём:** 41 проверка. Для каждого закрытого раздела выполняется обращение
от имени каждой из четырёх ролей и от имени неавторизованного посетителя.

### 4.5. Тестирование контракта программного интерфейса

**Цель:** проверка структуры ответов, действия параметров и соответствия
спецификации OpenAPI.

**Инструмент:** тестовый клиент Django, генератор drf-spectacular.

**Объём:** 33 проверки.

### 4.6. Нагрузочное тестирование

**Цель:** оценка времени отклика и доли ошибок при одновременной работе
нескольких десятков пользователей.

**Инструмент:** Locust.

**Профиль нагрузки:** три сценария с весами 7 : 2 : 1 — посетитель (реестры),
работа с картой (слои GeoJSON), аналитика (расчёты).

## 5. Критерии приёмки

### 5.1. Функциональные критерии

| № | Критерий | Пороговое значение |
|---|---|---|
| Ф-1 | Доля пройденных автотестов | 100 % |
| Ф-2 | Покрытие кода автотестами | не ниже 80 % |
| Ф-3 | Число дефектов уровня «критический» | 0 |
| Ф-4 | Число дефектов уровня «серьёзный» | 0 |
| Ф-5 | Число дефектов уровня «умеренный» | не более 5 |
| Ф-6 | Системные проверки Django (`check --deploy`) | без замечаний |
| Ф-7 | Полнота миграций (`makemigrations --check`) | без изменений |
| Ф-8 | Замечания анализатора стиля `ruff` | 0 |
| Ф-9 | Русский текст в английской версии интерфейса | только данные из базы |

### 5.2. Нефункциональные критерии

| № | Критерий | Пороговое значение |
|---|---|---|
| Н-1 | Время отклика страницы, 95-й процентиль | не более 1200 мс |
| Н-2 | Время отклика слоя карты, 95-й процентиль | не более 2000 мс |
| Н-3 | Доля ошибок под нагрузкой 50 пользователей | не более 1 % |
| Н-4 | Объём главной страницы без изображений | не более 350 КБ |
| Н-5 | Корректное отображение при ширине от 360 пикселей | во всех разделах |
| Н-6 | Работа в четырёх браузерах | без визуальных дефектов |
| Н-7 | Доступность с клавиатуры | все интерактивные элементы достижимы |

### 5.3. Критерии совместимости

| № | Критерий | Пороговое значение |
|---|---|---|
| С-1 | Набор автотестов на SQLite | 100 % пройдено |
| С-2 | Набор автотестов на PostgreSQL + PostGIS | 100 % пройдено |
| С-3 | Совпадение результатов пространственного поиска на обоих контурах | расхождение не более 0,01 км |

## 6. Классификация дефектов

| Уровень | Признак | Срок устранения |
|---|---|---|
| **Критический** | Система или ключевой раздел неработоспособны; потеря или искажение данных; обход разграничения доступа | Немедленно |
| **Серьёзный** | Функция не выполняет назначение; расчёт даёт неверный результат; раздел недоступен части пользователей | До завершения этапа |
| **Умеренный** | Функция работает с отклонением; неудобство, имеющее обходной путь | До приёмки |
| **Незначительный** | Дефект оформления, опечатка, несогласованность формулировок | По возможности |

## 8. Управление рисками испытаний

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| Расхождение поведения СУБД в пространственных запросах | Средняя | Высокое | Обязательный прогон набора на обоих контурах в среде непрерывной интеграции |
| Зависимость результата тестов от порядка выполнения | Средняя | Среднее | Сброс кеша между тестами приспособлением `clear_caches` |
| Недостаточность объёма данных для проверки производительности | Высокая | Среднее | Проверка на расширенном наборе (78 000 записей) |
| Невоспроизводимость результата кластеризации | Средняя | Среднее | Фиксация зерна генератора, отдельная проверка воспроизводимости |
| Отсутствие кириллического шрифта при формировании PDF | Низкая | Среднее | Перебор нескольких путей к шрифту с запасным вариантом |

## 9. Отчётность

По результатам испытаний оформляются:

- **[TEST_CASES.md](TEST_CASES.md)** — тест-кейсы с указанием шагов,
  ожидаемого и фактического результата;
- **[BUG_REPORTS.md](BUG_REPORTS.md)** — журнал выявленных дефектов с
  описанием причины и способа устранения;
- отчёт о покрытии кода (`htmlcov/index.html`, формируется командой
  `make cover`);
- протокол нагрузочного испытания (формируется Locust).

## 10. Условия завершения испытаний

Испытания считаются завершёнными при одновременном выполнении условий:

1. все автотесты пройдены на обоих контурах хранения;
2. все тест-кейсы выполнены и имеют отметку о результате;
3. дефекты уровней «критический» и «серьёзный» устранены и перепроверены;
4. достигнуты все пороговые значения раздела 5;
5. документация приведена в соответствие фактическому поведению системы.
