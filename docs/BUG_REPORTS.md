## Б-01. Нарушение ссылочной целостности при повторной загрузке данных

| | |
|---|---|
| **Уровень** | Критический |
| **Состояние** | Устранён, перепроверен |
| **Обнаружен** | 21.06.2026, ТК-47 |
| **Устранён** | 21.06.2026 |
| **Компонент** | `core/management/commands/load_seed.py` |
| **Контур** | SQLite |

### Описание

Повторный запуск команды загрузки с ключом `--truncate` завершался ошибкой
`IntegrityError: FOREIGN KEY constraint failed` на этапе записи таблицы
`infrastructure_objects`.

### Порядок воспроизведения

```bash
python backend/manage.py load_seed db/002_seed_data_scale1.sql --truncate
python backend/manage.py load_seed db/002_seed_data_scale1.sql --truncate
```

### Ожидаемое поведение

Обе загрузки завершаются успешно, число записей в каждой таблице остаётся
неизменным.

### Фактическое поведение

Первая загрузка проходит. Вторая прерывается на записи объектов
инфраструктуры с нарушением ограничения внешнего ключа.

### Причина

Django объявляет первичные ключи в SQLite как `INTEGER PRIMARY KEY
AUTOINCREMENT`. При таком объявлении счётчик хранится в служебной таблице
`sqlite_sequence` и **переживает удаление всех строк**. После очистки округа
получали идентификаторы 13–24 вместо 1–12, тогда как в поставляемом наборе
данных внешние ключи записаны явными числовыми значениями (`district_id = 2`),
предполагающими нумерацию с единицы.

Дефект не проявлялся при первой загрузке на пустую базу, из-за чего не был
обнаружен на этапе разработки.

### Устранение

Метод `_truncate` дополнен сбросом счётчиков первичных ключей с учётом типа
СУБД:

- **SQLite** — удаление соответствующих строк из `sqlite_sequence`;
- **PostgreSQL** — замена поочерёдного удаления одной инструкцией
  `TRUNCATE TABLE … RESTART IDENTITY CASCADE`, которая одновременно очищает
  таблицы, сбрасывает последовательности и снимает вопрос порядка удаления.

### Проверка

Добавлен автотест `test_commands.py::TestLoadSeedCommand::test_truncate_resets_identifiers`,
выполняющий двойную загрузку и проверяющий, что идентификаторы связанных
записей остаются корректными. Тест-кейс ТК-47 перепройден.

| **Компонент** | `exports/builders.py`, функция `build_pdf` |

### Описание

В сформированном документе PDF весь кириллический текст отображался
последовательностью прямоугольников.

### Порядок воспроизведения

1. Войти под учётной записью с ролью «Аналитик».
2. Открыть реестр объектов, выгрузить в формате PDF.
3. Открыть полученный файл.

### Ожидаемое поведение

Наименования объектов, адреса и заголовки колонок читаются.

### Фактическое поведение

Вместо русских букв выводятся прямоугольники. Латиница и цифры отображаются

### Причина

Библиотека `reportlab` по умолчанию использует встроенный шрифт Helvetica,
не содержащий кириллических начертаний. Символы за пределами набора
подставляются заменителем.

### Устранение

В функцию `build_pdf` добавлен перебор путей к системным шрифтам с
поддержкой кириллицы (DejaVu Sans, Liberation Sans, Arial) и регистрация
первого найденного. При отсутствии всех вариантов применяется встроенный
шрифт — формирование документа не прерывается, что важно для устойчивости
подсистемы выгрузки.

В образ контейнера добавлен пакет `fonts-dejavu-core`; соответствующая
строка внесена в `Dockerfile` с пояснением, почему пакет необходим.

### Проверка

Добавлен автотест `test_exports.py::TestPdf::test_pdf_signature`,
подтверждающий формирование корректного файла. Визуальная проверка
отображения кириллицы выполнена вручную по ТК-32.

## Б-03. Сброс порядка сортировки при переходе по страницам

| **Устранён** | 14.07.2026 |
| **Компонент** | `templates/partials/_pagination.html` |

### Описание

При переходе на вторую и последующие страницы реестра выбранный порядок
сортировки сбрасывался к значению по умолчанию; наложенные условия отбора
при этом сохранялись.

### Порядок воспроизведения

1. Открыть `/objects/`.
2. Нажать заголовок колонки «Мощность, т».
3. Перейти на вторую страницу.

### Ожидаемое поведение

Порядок сортировки сохраняется.

### Фактическое поведение

Записи выводятся в порядке по умолчанию (по наименованию).

### Причина

Ссылки постраничной навигации формировались конкатенацией строк с
использованием переменной `query_base`, в которую параметр `sort` не входил.
Формирование было выполнено цепочкой стандартных фильтров шаблона, что
затрудняло обнаружение ошибки при чтении кода.

### Устранение

Введён тег шаблона `{% query %}` (`core/templatetags/ff.py`), формирующий
строку запроса на основе текущей с заменой указанных параметров. Шаблон
постраничной навигации переписан с его использованием. Тот же тег применён
в панели выгрузки отчётов, что устранило потенциальную возможность
аналогичной ошибки.

Дополнительно введён тег `{% elided_range %}`: стандартный метод пагинатора
`get_elided_page_range` требует передачи номера текущей страницы, что
невозможно сделать напрямую из шаблона, и при вызове без аргументов
формировал многоточия относительно первой страницы.

### Проверка

Ручная проверка по ТК-09. Автотест
`test_views.py::TestFiltering::test_sorting_applied` подтверждает действие
сортировки.

## Б-04. Обратная связь модели перекрывала менеджер по умолчанию

| | |
|---|---|
| **Уровень** | Критический |
| **Состояние** | Устранён, перепроверен |
| **Обнаружен** | 05.07.2026, при формировании миграций |
| **Устранён** | 05.07.2026 |
| **Компонент** | `core/models.py` |

### Описание

Запуск любой команды управления завершался ошибкой
`AttributeError: 'ReverseManyToOneDescriptor' object has no attribute 'all'`.

### Порядок воспроизведения

```bash
python backend/manage.py makemigrations
```

### Ожидаемое поведение

Миграции формируются.

### Фактическое поведение

Ошибка возникает при загрузке модуля маршрутов на строке
`queryset = District.objects.all()`.

### Причина

Внешним ключам модели `InfrastructureObject`, указывающим на `District`,
`InfrastructureType` и `DataSource`, было присвоено имя обратной связи
`related_name="objects"`. Django создаёт атрибут с этим именем в целевой
модели, вследствие чего стандартный менеджер `objects` оказался перекрыт
дескриптором обратной связи.

Дефект носит скрытый характер: имя выглядит естественным для предметной
области («объекты округа»), а сообщение об ошибке не указывает на причину
прямо.

### Устранение

Имя обратной связи изменено на `facilities` во всех трёх внешних ключах.
Соответственно исправлены обращения в `core/views/registry.py`,
`console/views.py` и `api/views.py` — в них использовалось агрегирование
`Count("objects")`.

### Проверка

Формирование миграций и системная проверка `manage.py check` завершаются без
замечаний. Полный набор автотестов пройден.

не препятствует отправке запроса напрямую.

## Б-08. Пакетная загрузка нарушала порядок записи таблиц

| | |
|---|---|
| **Уровень** | Критический |
| **Состояние** | Устранён, перепроверен |
| **Обнаружен** | 26.07.2026, при проверке на расширенном наборе |
| **Устранён** | 26.07.2026 |
| **Компонент** | `core/management/commands/load_seed.py` |
| **Контур** | Оба |

### Описание

Загрузка расширенного набора данных (около 78 000 записей) завершалась
ошибкой `IntegrityError: FOREIGN KEY constraint failed`. Загрузка базового
набора (251 запись) тем же кодом проходила успешно.

### Порядок воспроизведения

```bash
python backend/manage.py load_seed db/002_seed_data_scale400.sql --truncate --batch 2000
```

### Ожидаемое поведение

Все записи загружаются с соблюдением ссылочной целостности.

### Фактическое поведение

Загрузка прерывается на фиксации первого пакета объектов инфраструктуры.

### Причина

Загрузчик выполнял один проход по файлу, накапливая записи в буферах по
таблицам, и сбрасывал буфер, как только тот достигал размера пакета. Порядок
сброса определялся порядком следования строк в файле, а не порядком
зависимостей между таблицами.

В базовом наборе ни один буфер не достигал порога в 1000 записей, поэтому все
буферы сбрасывались в конце — в правильном порядке, объявленном в
`TABLE_MODELS`. Дефект проявлялся только при объёме, превышающем размер
пакета.

Показательно, что увеличение объёма данных не просто замедлило работу, а
изменило порядок операций и тем самым обнажило скрытую ошибку логики.

### Устранение

Загрузчик переписан на проход по одной таблице за раз: файл читается столько
раз, сколько в системе доменных таблиц, в порядке их объявления. Порядок
записи теперь не зависит ни от объёма данных, ни от размера пакета.

Рассмотренная альтернатива — накопление всех записей в памяти с последующей
записью — отвергнута: 78 000 объектов модели потребовали бы сотен мегабайт.
При построчном проходе объём памяти ограничен размером пакета независимо от
объёма файла.

Затраты на повторное чтение невелики: полная загрузка расширенного набора
занимает 11,4 с.

### Проверка

Загрузка расширенного набора выполнена на обоих контурах хранения. Автотест
`test_commands.py::TestLoadSeedCommand::test_truncate_resets_identifiers`
подтверждает сохранение ссылочной целостности при повторной загрузке.

## Б-09. Неоднозначное имя колонки в пространственных запросах

| | |
|---|---|
| **Уровень** | Критический |
| **Состояние** | Устранён, перепроверен |
| **Обнаружен** | 26.07.2026, при прогоне набора на PostgreSQL |
| **Устранён** | 26.07.2026 |
| **Компонент** | `geo/queries.py` |
| **Контур** | PostgreSQL — отказ; SQLite — неверный результат без сообщения |

### Описание

Отбор объектов по видимой области карты и поиск ближайших завершались на
PostgreSQL ошибкой `ProgrammingError: column reference "geom" is ambiguous`.

### Порядок воспроизведения

```bash
FF_DB_ENGINE=postgres pytest tests/test_views.py::TestMapLayers -q
```

### Ожидаемое поведение

Запросы выполняются, слой формируется.

### Фактическое поведение

СУБД отклоняет запрос как содержащий неоднозначную ссылку на колонку.

### Причина

Выражения передавались в SQL с неполным именем колонки — `geom` вместо
`"таблица"."geom"`. Выборка объектов инфраструктуры соединяется со
справочником административных округов, у которого имеется **собственная
колонка `geom`** — границы округа. При соединении двух таблиц с одноимёнными
колонками неполное имя становится неоднозначным.

**Наиболее существенное обстоятельство:** на SQLite тот же код не давал
ошибки. Прикладная реализация обращалась к геометрии через ORM по имени поля
модели, поэтому неоднозначность не возникала вовсе. Дефект проявлялся
исключительно на промышленном контуре и был бы обнаружен только при
развёртывании.

Более того, если бы неполное имя попало в выражение, исполняемое SQLite,
СУБД разрешила бы неоднозначность молча, выбрав первую подходящую колонку, —
то есть выдала бы **неверный результат, не сообщив об ошибке**. Такой дефект
обнаружить существенно труднее, чем отказ запроса.

### Устранение

Введена вспомогательная функция `_qualified(qs, field)`, формирующая полное
имя колонки вида `"таблица"."колонка"` по метаданным модели. Функция
применена во всех трёх выражениях, передаваемых в SQL: отбор по
прямоугольнику, вычисление расстояния и отбор по радиусу.

Функция снабжена пояснением, указывающим причину необходимости квалификации,
чтобы при добавлении новых пространственных выражений требование не было
упущено.

### Проверка

Полный набор автотестов пройден на PostgreSQL с расширением PostGIS.
Результаты пространственного поиска на двух контурах совпадают с расхождением
не более 0,004 км (ТК-48).

### Извлечённый урок

Дефект подтверждает целесообразность обязательного прогона набора автотестов
на обоих контурах хранения — критерий С-2 плана испытаний. Проверка только на
контуре разработки не выявила бы ошибку ни при каких условиях.

## Б-10. Инструкция TRUNCATE неприменима внутри транзакции

| | |
|---|---|
| **Уровень** | Умеренный |
| **Состояние** | Устранён, перепроверен |
| **Обнаружен** | 26.07.2026, при прогоне набора на PostgreSQL |
| **Устранён** | 26.07.2026 |
| **Компонент** | `core/management/commands/load_seed.py` |
| **Контур** | PostgreSQL |

### Описание

Вызов команды загрузки с ключом `--truncate` из автотеста завершался ошибкой
`OperationalError: cannot TRUNCATE "etl_log" because it has pending trigger
events`.

### Порядок воспроизведения

```bash
FF_DB_ENGINE=postgres pytest tests/test_commands.py -q
```

### Ожидаемое поведение

Команда выполняется независимо от того, вызвана она из командной строки или
из кода внутри транзакции.

### Фактическое поведение

При открытой транзакции с отложенными проверками внешних ключей PostgreSQL
отклоняет инструкцию `TRUNCATE`.

### Причина

Очистка таблиц выполнялась одной инструкцией `TRUNCATE ... RESTART IDENTITY
CASCADE`. Инструкция эффективна и корректна при вызове из командной строки, но
неприменима внутри открытой транзакции, содержащей отложенные проверки
ссылочной целостности. Такая ситуация возникает при выполнении автотестов, где
каждая проверка обёрнута в транзакцию.

### Устранение

Добавлена проверка `connection.in_atomic_block`. Вне транзакции применяется
`TRUNCATE`; внутри транзакции — удаление строк с последующим явным сбросом
последовательностей через `ALTER SEQUENCE ... RESTART WITH 1`.

Сброс последовательностей необходим в обоих случаях: в поставляемых наборах
внешние ключи записаны явными числовыми значениями, предполагающими нумерацию
с единицы.

### Проверка

Полный набор автотестов пройден на PostgreSQL. Ручная загрузка расширенного
набора из командной строки продолжает использовать `TRUNCATE`.

## Б-11. Выпадающее меню закрывалось при переходе к подразделу

| | |
|---|---|
| **Уровень** | Серьёзный |
| **Состояние** | Устранён, перепроверен |
| **Обнаружен** | 29.07.2026, при работе с интерфейсом |
| **Устранён** | 29.07.2026 |
| **Компонент** | `static/css/app.css` |

### Описание

Выпадающее меню раздела закрывалось прежде, чем указатель достигал нужного
подраздела. Переход выполнялся лишь при быстром движении указателя по прямой.

### Порядок воспроизведения

1. Навести указатель на пункт меню с вложенными разделами.
2. Начать движение к подразделу в выпавшем окне.

### Причина

Окно отстоит от пункта меню на шесть пикселей — этот отступ задан для
зрительного разделения. Указанные шесть пикселей не принадлежат ни пункту, ни
окну: пересекая их, указатель терял наведение на обоих элементах, и окно
скрывалось.

Дефект относится к разряду тех, что не обнаруживаются автоматической
проверкой: разметка корректна, стили применяются, ошибок не возникает.
Проявляется он только при работе живого человека с указателем.

### Устранение

Добавлен псевдоэлемент, расширяющий область наведения окна вверх на высоту
отступа. Поскольку окно вложено в пункт меню, наведение на перемычку
сохраняет наведение и на сам пункт. Дополнительно введена задержка скрытия в
120 мс — она делает переход спокойным и прощает небольшое отклонение
указателя.

## Б-13. Смещения разбора в байтах при автоматической разметке

| | |
|---|---|
| **Уровень** | Умеренный |
| **Состояние** | Устранён |
| **Обнаружен** | 30.07.2026, при разработке инструмента разметки |
| **Устранён** | 30.07.2026 |
| **Компонент** | `tools/mark_translatable.py` |

### Описание

Инструмент автоматической разметки строк для перевода расставлял закрывающие
скобки не на своих местах, порождая синтаксически неверный код.

### Причина

Модуль `ast` сообщает положение узлов в **байтах представления UTF-8**, а не
в символах. Для кириллицы эти величины расходятся вдвое, поэтому вычисленное
по символам положение оказывалось смещённым.

### Устранение

Правка выполняется над двоичным представлением строк: положения,
сообщённые разбором, применяются к байтам, после чего результат
декодируется обратно.

Дополнительно инструмент проверяет синтаксис результата **до записи** и
отказывается сохранять файл, если разбор не удался. Именно эта проверка
предотвратила повреждение девяти файлов при первом запуске.

### Описание

Загрузка данных завершалась трассировкой отказа при выводе отчёта. Данные
при этом были записаны: отказ наступал после работы, на её описании.

### Порядок воспроизведения

1. Открыть консоль с кодовой страницей cp1251 (русская Windows).
2. Выполнить `python backend/manage.py etl --all --offline`.

### Ожидаемое поведение

Отчёт выводится целиком, команда завершается кодом 0.

`UnicodeEncodeError: 'charmap' codec can't encode character '²'` на строке
отчёта конвейера зон ограничения. Код завершения — 1.

Сообщения команд набраны по-русски и содержат знаки вроде «км²», которых нет

системы, и знак вне её набора прерывал команду.

### Устранение

Потоки вывода приводятся к UTF-8 при запуске утилиты командной строки.
Знаки, которые консоль показать не может, заменяются: оформление отчёта
не должно решать судьбу команды. Успешный код завершения на консоли
с однобайтовой кодировкой проверяется автотестом.
