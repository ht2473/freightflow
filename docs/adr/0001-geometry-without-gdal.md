# ADR-0001. Пространственный слой без GDAL и django.contrib.gis

- **Статус:** принято
- **Дата:** 2026-06-18
- **Контекст:** выбор способа работы с пространственными данными

## Контекст

Система хранит и отображает пространственные данные: точки размещения
объектов инфраструктуры, ломаные участков дорожной сети и грузовых коридоров,
условные центры административных округов. Требуются операции: сохранение и
чтение геометрии, отбор объектов в границах видимой области карты, поиск
ближайших объектов к произвольной точке, расчёт протяжённости.

Штатное средство Django для таких задач — приложение `django.contrib.gis`.
Оно требует установки системных библиотек GDAL, GEOS и PROJ.

## Рассмотренные варианты

### Вариант 1. `django.contrib.gis` с полным набором зависимостей

*Достоинства:* полнофункциональный набор пространственных операций, знакомый
интерфейс, поддержка проекций.

*Недостатки:*

- установка GDAL на Windows требует подбора совместимых сборок и настройки
  переменных окружения; типовая ошибка `OSError: could not find the GDAL
  library` — распространённое препятствие при развёртывании;
- автотесты невозможно выполнять на SQLite: требуется расширение SpatiaLite,
  что усложняет среду непрерывной интеграции;
- образ контейнера увеличивается примерно на 300 МБ;
- фактически используются четыре операции из нескольких десятков доступных.

### Вариант 2. Хранение координат в отдельных числовых полях

*Достоинства:* предельная простота, отсутствие зависимостей.

*Недостатки:* непригоден для ломаных линий — участки дорожной сети содержат
от двух до нескольких десятков вершин; исключает применение пространственных
индексов; смешивает представление данных с их структурой.

### Вариант 3. Собственный тонкий слой поверх возможностей СУБД (принят)

Геометрия хранится в родном типе PostgreSQL (`geometry`) либо в текстовом
представлении WKT (SQLite). Преобразование выполняется полем модели через два
документированных хука Django.

*Достоинства:*

- отсутствие системных зависимостей: установка сводится к `pip install`;
- один и тот же прикладной код работает на обоих контурах хранения;
- автотесты выполняются на SQLite без дополнительных расширений;
- в промышленном контуре доступны индексируемые функции PostGIS.

*Недостатки:*

- набор операций ограничен реализованными;
- преобразование проекций не поддерживается — система работает
  исключительно в WGS-84;
- на SQLite поиск ближайших выполняется в два этапа и медленнее, чем по
  пространственному индексу.

## Решение

Принят вариант 3.

Реализация опирается на два хука поля модели Django:

- `select_format(compiler, sql, params)` — при чтении оборачивает колонку в
  `ST_AsText(...)`, если СУБД является PostgreSQL; на SQLite возвращает
  значение без изменений;
- `get_placeholder(value, compiler, connection)` — при записи возвращает
  `ST_GeomFromText(%s, 4326)` для PostgreSQL и `%s` для SQLite.

Оба хука входят в публичный интерфейс `django.db.models.Field` и присутствуют
в Django 6; их наличие подтверждено по исходным текстам используемой версии.

Пространственные запросы выбирают реализацию по `connection.vendor`:

| Операция | PostgreSQL + PostGIS | SQLite |
|---|---|---|
| Отбор в прямоугольнике | `geom && ST_MakeEnvelope(...)` по индексу GiST | Разбор WKT и сравнение координат |
| Поиск ближайших | `ST_DWithin` и сортировка по `ST_Distance` | Отбор по прямоугольнику, затем гаверсинус |
| Протяжённость | `ST_Length(geography)` | Сумма гаверсинусов по вершинам |

## Последствия

**Положительные.** Развёртывание на Windows выполняется без установки
системных библиотек. Среда непрерывной интеграции не требует контейнера с
пространственным расширением для быстрого прогона. Демонстрационная база
SQLite поставляется в составе репозитория, и система запускается сразу после
клонирования.

**Отрицательные.** Добавление новой пространственной операции требует
реализации для обеих СУБД. Поиск ближайших на SQLite при объёме свыше
нескольких десятков тысяч записей заметно медленнее; для промышленной
эксплуатации предписан PostgreSQL.

**Проверка.** Корректность слоя подтверждена автотестами `tests/test_geo.py`
(35 проверок) и сквозным сопоставлением результатов поиска ближайших на обоих
контурах: расстояния совпадают с точностью до третьего знака.
