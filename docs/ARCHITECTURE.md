# Архитектура ИС «ГрузПоток»

Документ описывает организацию системы, принятые архитектурные решения и
основания для них. Отдельные решения, потребовавшие развёрнутого обоснования,
вынесены в записи [ADR](adr/).

---

## 1. Общая организация

Система построена на платформе Django и следует многослойной организации.
Каждый слой имеет одну зону ответственности и не обращается через голову
соседнего.

```
        Браузер                        Внешний потребитель
           │                                    │
           ▼                                    ▼
   ┌───────────────┐                   ┌────────────────┐
   │  Шаблоны      │                   │   REST API     │
   │  (HTML, CSS)  │                   │ (DRF, OpenAPI) │
   └───────┬───────┘                   └────────┬───────┘
           │                                    │
           ▼                                    ▼
   ┌───────────────────────────────────────────────────┐
   │  Представления                                    │
   │  подготовка контекста, разбор параметров отбора   │
   └───────────────────────┬───────────────────────────┘
                           │
         ┌─────────────────┴──────────────────┐
         ▼                                    ▼
 ┌────────────────┐                  ┌─────────────────┐
 │  selectors     │                  │  analytics      │
 │  агрегаты,     │                  │  индекс, k-mean,│
 │  кеширование   │                  │  прогноз, сцен. │
 └───────┬────────┘                  └────────┬────────┘
         │                                    │
         └─────────────────┬──────────────────┘
                           ▼
                 ┌───────────────────┐
                 │  Модели (ORM)     │
                 │  11 сущностей     │
                 └─────────┬─────────┘
                           │
                 ┌─────────▼─────────┐
                 │  geo              │
                 │  геометрия, WKT,  │
                 │  простр. запросы  │
                 └─────────┬─────────┘
                           ▼
              ┌────────────────────────┐
              │  PostgreSQL + PostGIS  │
              │          или SQLite    │
              └────────────────────────┘
```

**Ключевое свойство организации:** представления не содержат запросов к базе
сложнее выборки одной записи. Всё, что требует агрегации, вынесено в
`core/selectors.py`; всё, что требует расчёта, — в `analytics/services.py`.
Благодаря этому аналитические функции проверяются автотестами без обращения к
слою HTTP, а изменение способа отображения не затрагивает логику расчёта.

## 2. Состав модулей

| Модуль | Ответственность |
|---|---|
| `config` | Настройки, корневая маршрутизация, точки входа WSGI и ASGI |
| `core` | Предметная область: модели, выборки, реестры, карта, мониторинг |
| `geo` | Пространственный слой: геометрия, поля модели, запросы |
| `etl` | Загрузка данных: конвейер, проверки качества, карантин, регламент |
| `analytics` | Индекс нагрузки, кластеризация, прогнозирование, сценарии |
| `accounts` | Роли, профили, личный кабинет, журнал аудита |
| `content` | Аналитические материалы, обратная связь, информационные страницы |
| `console` | Панель администратора системы |
| `exports` | Формирование отчётов в пяти форматах |
| `api` | REST API со спецификацией OpenAPI |

Зависимости между модулями направлены в одну сторону: `core` не знает о
`console`, `exports`, `etl` и `api`, но все они обращаются к `core`. Это
позволяет отключить любой из прикладных модулей, не нарушив работу предметной
области.

### Подсистема загрузки

Источники разнородны, порядок работы с ними один. Он задан конвейером и
одинаков для программного интерфейса OpenStreetMap, статистической публикации,
перечня, ведущегося вручную, и файла, присланного пользователем.

| Этап | Что делает | Где определён |
|---|---|---|
| Получение | Забирает выгрузку у источника | `Pipeline.extract` |
| Приведение | Превращает её в записи доменной модели и выполняет отбор | `Pipeline.prepare` |
| Проверка | Применяет объявленные проверки качества | `etl.quality` |
| Запись | Обновляет запись по ключу источника либо создаёт новую | `ModelPipeline.write` |
| Журнал | Записывает счётчики и откладывает отклонённые записи | `etl.pipeline.run` |

Общий порядок нужен не сам по себе: он делает поведение источников
сопоставимым. Загрузка любого набора отвечает на одни и те же вопросы —
сколько записей поступило, сколько из них новых, сколько изменилось, сколько
отклонено и по какой причине. Без него эти величины у каждого загрузчика
считались бы по-своему и не складывались бы в оценку состояния данных.

**Инкрементальность** обеспечивается сравнением по существу: геометрия
сопоставляется в текстовом представлении с той точностью, с какой хранится,
числа — как числа, ссылки — по идентификатору. Отметка о времени выгрузки
в сравнении не участвует, иначе каждая загрузка выглядела бы полным
обновлением реестра.

**Отбор отделён от проверки.** Элемент выгрузки, не относящийся к предметной
области, отсеивается и учитывается отдельным счётчиком; в карантин попадает
только то, что должно было стать записью, но не прошло требований к качеству.

**Регламент** объявляет сам набор данных, а срок отсчитывается от последней
успешной загрузки. Задания выполняет исполнитель Celery с планировщиком;
в контуре без очереди тот же состав определяет системный таймер по команде
`manage.py etl --due`.

## 3. Модель предметной области

Тринадцать сущностей делятся на четыре группы.

**Справочники** — `District`, `InfrastructureType`, `CargoCategory`,
`DataSource`. Изменяются редко, ссылки на них защищены от удаления
(`on_delete=PROTECT`): удаление типа объекта, на который ссылаются записи,
привело бы к потере смысла этих записей.

**Реестры** — `InfrastructureObject`, `RoadSegment`, `CargoRoute`. Содержат
пространственную привязку. Наполняются процедурами загрузки.

**Наблюдения** — `TrafficCondition`, `TrafficIncident`, `FreightFlowStat`.
Накапливаются во времени, объём растёт линейно. Для них определены индексы
по полям времени и внешним ключам.

**Служебные** — `EtlRun`, `EtlReject`. Журнал загрузок и карантин отклонённых
записей. Карантин связан с журналом каскадным удалением: запись об отклонении
без записи о загрузке смысла не имеет.

### Производные характеристики

Расчётные величины реализованы свойствами моделей, а не полями базы:
загруженность участка в словесной форме, длительность инцидента, средняя
скорость маршрута, удельная мощность объекта. Хранение таких величин
потребовало бы их синхронизации при каждом изменении исходных полей, тогда
как стоимость вычисления пренебрежимо мала.

## 4. Пространственный слой

Решение отказаться от `django.contrib.gis` подробно обосновано в
[ADR-0001](adr/0001-geometry-without-gdal.md). Кратко:

- геометрия хранится в поле типа `geometry` (PostgreSQL) или `text` (SQLite);
- на прикладном уровне представлена классом `geo.Geometry` — неизменяемым
  объектом с методами преобразования в WKT и GeoJSON и метриками;
- преобразование выполняется полем `geo.fields.GeometryField` через два хука
  Django: `select_format` (оборачивает колонку в `ST_AsText` при чтении) и
  `get_placeholder` (оборачивает значение в `ST_GeomFromText` при записи);
- пространственные запросы (`in_bbox`, `nearest`) выбирают реализацию по типу
  СУБД: на PostGIS — индексируемые `ST_DWithin` и `ST_Distance`, на SQLite —
  предварительный отбор по прямоугольнику с последующим уточнением расстояния
  по формуле гаверсинуса в Python.

Прикладной код при этом одинаков для обоих контуров: `nearest(queryset, lon,
lat, radius, limit)` вызывается без указания используемой СУБД.

## 5. Аналитическое ядро

Реализовано на стандартной библиотеке Python без `numpy` и `scikit-learn`.
Основание: объём данных — двенадцать округов и несколько десятков тысяч
записей — не требует векторизованных вычислений, а отказ от тяжёлых
зависимостей упрощает развёртывание и делает алгоритмы прозрачными для
проверки в рамках квалификационной работы.

**Композитный индекс нагрузки.** Четыре разнородных показателя нормируются
методом «минимум — максимум», умножаются на веса (0,30 / 0,30 / 0,25 / 0,15)
и суммируются. Индекс отражает относительное положение округа в выборке.

**Типология.** Метод k-средних в пространстве стандартизованных признаков,
инициализация по схеме k-means++, генератор случайных чисел зафиксирован ради
воспроизводимости результата.

**Прогнозирование.** Линейный тренд по методу наименьших квадратов; на
помесячных рядах к нему добавляется сезонная поправка как среднее отклонение
месяца от линии тренда, на годовых внутригодового профиля нет и поправка
не оценивается. Качество измеряется на отложенной выборке — на хвосте ряда,
которого модель при обучении не видела.

**Сценарное моделирование.** Эластичный отклик загруженности на изменение
объёма перевозок (коэффициент 0,6) и пропускной способности сети
(коэффициент −0,4) с последующим повторным нормированием.

## 6. Кеширование

Агрегированные сводки кешируются на пять минут, аналитические расчёты — на
время, заданное `FF_ANALYTICS_CACHE_TTL` (по умолчанию десять минут).
Ключи кеша сгруппированы по префиксам, что позволяет сбрасывать их выборочно.

Сброс выполняется в трёх случаях: после загрузки данных из источника, по
команде администратора из панели управления и по истечении срока.

В контуре с одним рабочим процессом используется кеш в оперативной памяти
процесса; при нескольких процессах требуется Redis, адрес которого задаётся
переменной `FF_REDIS_URL`.

## 7. Разграничение доступа

Роль хранится в профиле пользователя (`accounts.UserProfile.role`) и
проверяется декораторами представлений. Дополнительно создаются группы
разрешений Django (`role:viewer`, `role:analyst`, …) — они дают привычный
набор прав в штатной админке.

Модель вложенная: свойство `has_role` сравнивает порядковые номера ролей,
поэтому администратор автоматически обладает правами всех младших ролей.

Значимые действия — вход, изменение данных, выгрузка, административные
операции — фиксируются в `accounts.AuditEvent`. Обращения к страницам
просмотра в журнал не записываются: их объём сделал бы журнал непригодным для
разбора инцидентов.

## 8. Клиентская часть

Страницы отрисовываются на сервере. Клиентский сценарий добавляет поведение:
переключение оформления, работу меню на узких экранах, построение графиков и
взаимодействие с картой. Страницы полностью работоспособны до загрузки
сценария.

Внешние зависимости сведены к минимуму. Карта строится на MapLibre GL
(1,0 МБ, 274 КБ в сжатом виде); библиотека размещена в составе проекта
и загружается только на странице карты. Библиотека визуализации не
используется — графики строятся собственным кодом средствами SVG (около
200 строк). Такой подход экономит примерно 200 КБ на странице и позволяет
оформлять графики теми же переменными CSS, что и остальной интерфейс,
в том числе корректно перекрашивать их при смене темы.

Карта получает данные векторными тайлами со своего домена: сторонние
тайловые службы не используются. Слои, их свойства и масштабы описаны
одним реестром на стороне сервера (`core/tilelayers.py`), тайл собирается
и упаковывается средствами `geo/tiles.py` и `geo/mvt.py`. Отбор по округу
и типу, включение слоёв и раскраска округов по показателю выполняются
выражениями стиля на уже полученном тайле, без обращения к серверу.

Оформление построено на системе переменных CSS с двумя темами. Семафорная
шкала состояний (зелёный → янтарный → красный) применяется единообразно на
карте, в таблицах, на графиках и в значках состояний.

## 9. Формирование отчётов

Набор данных описывается объектом `Dataset` — перечнем колонок с функциями
извлечения значений и выборкой записей. Построитель конкретного формата
отвечает только за представление. Благодаря такому разделению добавление
формата не затрагивает наборы данных, а добавление набора не затрагивает
построители.

Файлы сохраняются в каталог `EXPORT_ROOT` и выдаются через представление,
проверяющее принадлежность файла запросившему пользователю. Прямой доступ к
каталогу по HTTP закрыт настройкой обратного прокси.

## 10. Совместимость СУБД

Система работает на двух контурах хранения.

| Свойство | PostgreSQL + PostGIS | SQLite |
|---|---|---|
| Назначение | Промышленная эксплуатация | Разработка, автотесты, демонстрация |
| Геометрия | Тип `geometry(…, 4326)` | Текст в формате WKT |
| Пространственный поиск | `ST_DWithin` по индексу GiST | Отбор по прямоугольнику и гаверсинус |
| Полнотекстовый поиск | Триграммный индекс `pg_trgm` | `LIKE` с приведением регистра |
| Файл базы в репозитории | Нет | Да, для немедленного запуска |

Один и тот же набор автотестов выполняется на обоих контурах в среде
непрерывной интеграции: ошибка в выражении SQL для одной СУБД не
обнаруживается проверкой другой.

## 11. Наблюдаемость

Журналирование настроено на три потока: обращения к приложению, ошибки и
события безопасности. Каждому запросу присваивается идентификатор, который
попадает в записи журнала и выводится в подвале страницы — это позволяет
сопоставить жалобу пользователя с конкретной записью журнала.

Конечная точка `/healthz` возвращает состояние соединения с базой и объёмы
ключевых таблиц; предназначена для системы мониторинга и проверки готовности
контейнера.

## 12. Интернационализация

Интерфейс доступен на русском и английском языках. Механизм — штатный для
Django: строки помечаются вызовом отложенного перевода `gettext_lazy` в коде
и тегом `{% trans %}` в шаблонах, переводы хранятся в каталоге
`backend/locale/`.

**Что переводится.** Весь интерфейс: навигация, заголовки разделов, подписи
полей, кнопки, заголовки таблиц, наименования показателей, оценки состояния
движения, сообщения системы и пояснительные тексты в разделах методологии и
справки — свыше 1100 строк.

**Что не переводится.** Данные из базы: наименования объектов, округов,
источников, тексты аналитических материалов. Это содержание, а не интерфейс;
их перевод потребовал бы отдельных полей в модели для каждого языка, что для
справочных данных городского масштаба неоправданно.

### Отложенный перевод и сериализация

Строки помечаются `gettext_lazy`, а не `gettext`: значение вычисляется в
момент вывода, когда язык уже выбран, а не в момент импорта модуля.

Побочное следствие обнаружилось при разметке заголовков графиков: отложенная
строка — объект, а не `str`, и стандартный кодировщик JSON её не принимает.
Решение — кодировщик `DjangoJSONEncoder`, приводящий такие объекты к строке
при сериализации.

### Подписи, хранимые в базе

Описания действий в журнале аудита сохраняются на русском языке — он же
служит ключом перевода. Перевод выполняется **при выводе** фильтром
`translated`, а не при записи: иначе язык записи фиксировался бы тем, что был
выбран в момент действия, и не менялся бы при переключении интерфейса.

### Инструменты сопровождения

Два вспомогательных сценария в каталоге `tools/`:

* `mark_translatable.py` — разметка строк по разбору синтаксического дерева.
  Разбор, а не регулярные выражения: литерал, записанный в несколько строк
  через неявную склейку, образует один узел дерева, тогда как построчная
  обработка разрывает его и порождает неверный код. Инструмент проверяет
  синтаксис результата до записи и отказывается сохранять повреждённый файл.

* `fill_translations.py` — наполнение файла переводов по словарю. Отдельно
  обрабатывает пометку «неточно», которую `msgmerge` проставляет при
  обновлении: подбор ведётся по написанию, а не по смыслу, и результат бывает
  ошибочным.

## 13. Отделение служебных сведений от пользовательских

Сведения, полезные при разборе неисправностей, не показываются в разделах,
предназначенных пользователю:

| Сведение | Где доступно |
|---|---|
| Идентификатор запроса | Журнал сервера, панель администратора |
| Адрес обращения и IP | Журнал аудита панели администратора |
| Имена таблиц базы данных | Панель администратора, документация |
| Внутренние коды справочников | Административная панель Django |
| Имена наборов данных выгрузки | Журнал сервера |

В пользовательских разделах на их месте выводятся наименования разделов и
понятные описания действий. Разделение проведено намеренно: показ служебных
подробностей создаёт впечатление незавершённости и не помогает тому, кто с
системой работает, а не сопровождает её.
