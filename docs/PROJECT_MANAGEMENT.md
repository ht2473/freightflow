# Организация работ по проекту «ГрузПоток»

Документ описывает применённый подход к управлению проектом, его обоснование
и фактические результаты.

---

## 1. Выбор подхода

### 1.1. Условия проекта

| Условие | Значение |
|---|---|
| Численность исполнителей | Один человек |
| Срок | Восемь недель |
| Определённость требований | Высокая: перечень зафиксирован в задании |
| Определённость технических решений | Низкая: способ работы с пространственными данными предстояло выбрать |
| Заказчик | Аттестационная комиссия; промежуточная приёмка не предусмотрена |

### 1.2. Рассмотренные подходы

**Каскадная модель.** Последовательное выполнение этапов с полным завершением
каждого. Соответствует высокой определённости требований, но не допускает
раннего обнаружения технических затруднений: выбор способа работы с
геометрией был бы проверен только на этапе реализации, когда изменение
решения потребовало бы переработки.

**Scrum в полном объёме.** Предполагает распределение ролей — владелец
продукта, руководитель команды, команда разработки — и регулярные совещания
между ними. При единственном исполнителе роли вырождаются, а совещания
теряют смысл: обсуждать не с кем.

**Комбинированный подход (принят).** Планирование по PMBoK — устав,
иерархическая структура работ, реестр рисков — с итеративным выполнением по
принципам Scrum: короткие итерации, поставляемый результат в конце каждой,
пересмотр плана по итогам.

### 1.3. Обоснование выбора

Планирование по PMBoK даёт то, чего недостаёт итеративному подходу при
единственном исполнителе: явную фиксацию границ проекта и перечня требований.
Без этого высок риск незаметного расширения объёма работ — риск Р-08.

Итеративное выполнение даёт то, чего недостаёт каскадной модели: возможность
проверить техническое решение на работающем коде и изменить его, пока
зависимости от него немногочисленны.

Практики, лишённые смысла при одном исполнителе, не применялись: ежедневные
совещания, оценка в условных единицах трудоёмкости, ретроспективы в форме
обсуждения. Вместо ретроспективы велась запись извлечённых уроков —
результат фиксировался в реестре рисков и записях ADR.

## 2. Итерации

Продолжительность итерации — одна неделя. Каждая завершается проверяемым
результатом.

| № | Период | Содержание | Результат итерации |
|---|---|---|---|
| 1 | Недели 1–2 | Анализ требований и данных, выбор технических средств, схема базы, пространственный слой | Миграции применяются на обеих СУБД, геометрия сохраняется и читается |
| 2 | Неделя 3 | Модели предметной области, агрегированные выборки, процедуры загрузки | Данные загружаются, сводки формируются, автотесты моделей проходят |
| 3 | Недели 4–5 | Дизайн-система, каркас, публичные разделы, карта | Все публичные разделы отвечают, слои карты загружаются |
| 4 | Неделя 6 | Аналитическое ядро, разграничение доступа, программный интерфейс | Расчёты выполняются, полномочия разграничены, API документирован |
| 5 | Неделя 7 | Формирование отчётов, личный кабинет, панель администратора | Пять форматов формируются, все разделы доступны |
| 6 | Неделя 8 | Испытания, исправление дефектов, документация, развёртывание | Критерии приёмки достигнуты |

### 2.1. Порядок внутри итерации

**Начало.** Уточнение состава работ итерации по иерархической структуре,
проверка актуальности реестра рисков.

**Выполнение.** Работа с ведением записей о принятых решениях. Существенные
решения оформляются записями ADR по мере принятия, а не задним числом.

**Завершение.** Прогон полного набора автотестов, сопоставление
результата с перечнем требований, запись извлечённых уроков.

### 2.2. Отклонения от плана

| Итерация | Отклонение | Причина | Реакция |
|---|---|---|---|
| 1 | Продлена до двух недель | Файл схемы в исходном репозитории отсутствовал; схему потребовалось восстанавливать по инструкциям вставки | План пересмотрен, срок последующих итераций сохранён за счёт объединения работ по интерфейсу |
| 3 | Продлена до двух недель | Объём работ по интерфейсу оценён заниженно: около пятидесяти шаблонов вместо предполагавшихся тридцати | Часть работ по наполнению перенесена в итерацию 5 |
| 4 | Выполнена досрочно | Аналитическое ядро на стандартной библиотеке оказалось менее трудоёмким, чем предполагалось | Высвободившееся время направлено на автотесты |

## 3. Управление объёмом работ

### 3.1. Фиксация требований

Перечень требований зафиксирован в [уставе проекта](PROJECT_CHARTER.md) с
указанием способа проверки каждого. При завершении итерации выполнялось
сопоставление реализованного с перечнем.

### 3.2. Обращение с предложениями по развитию

Идеи, возникавшие в ходе работы и не входившие в подтверждённые требования,
записывались отдельно и не реализовывались. Примеры отклонённых предложений:

- построение маршрутов между объектами инфраструктуры;
- уведомления в браузере в реальном времени;
- редактор геометрии на карте;
- сопоставление показателей с другими городами.

Каждое из перечисленных увеличило бы объём работ на несколько дней при
отсутствии соответствующего требования.

### 3.3. Результат

Реализованы все четырнадцать функциональных и восемь нефункциональных
требований. Работы, не входящие в объём, не выполнялись.

## 4. Управление качеством

### 4.1. Встроенные проверки

| Уровень | Средство | Периодичность |
|---|---|---|
| Стиль кода | `ruff` | При каждом изменении |
| Корректность | Набор автотестов | При завершении пакета работ |
| Конфигурация | `manage.py check --deploy` | При завершении итерации |
| Совместимость СУБД | Прогон набора на двух контурах | При завершении итерации |
| Производительность | Locust | Итерация 6 |

### 4.2. Подход к автотестам

Тесты писались не только после реализации, но и как средство обнаружения
дефектов в граничных случаях. Показательный пример: дефект
[Б-07](BUG_REPORTS.md#б-07) выявлен при написании теста для пустой базы
данных и потребовал изменения кода, а не ожиданий теста.

Четыре из семи выявленных дефектов относятся к граничным случаям, ни один из
которых не проявлялся в штатном сценарии использования.

### 4.3. Обращение с дефектами

Дефекты уровней «критический» и «серьёзный» устранялись в день обнаружения с
добавлением автотеста, исключающего повторное появление. Дефекты уровней
«умеренный» и ниже накапливались до завершения текущего пакета работ.

## 5. Управление рисками

Реестр рисков ([RISKS.md](RISKS.md)) составлен на этапе планирования и
пересматривался при завершении каждой итерации.

**Наиболее значимое решение по управлению рисками** — отказ от библиотек
геообработки (риск Р-01). Решение принято до начала разработки, на этапе
выбора технических средств, и предотвратило вероятную блокировку работ на
неопределённый срок.

**Реализовавшиеся риски.** Два из тринадцати: Р-03 (коллизия имён при
определении моделей) и Р-06 (отсутствие кириллического шрифта). Оба устранены
в день обнаружения без влияния на срок.

Риск Р-03 не был выявлен на этапе планирования. Это отражено в реестре как
извлечённый урок: имена обратных связей моделей следует проверять на
совпадение с атрибутами, определяемыми фреймворком.

## 6. Фиксация архитектурных решений

Существенные решения оформлялись записями ADR с указанием рассмотренных
вариантов, оснований выбора и последствий.

| Запись | Решение |
|---|---|
| [ADR-0001](adr/0001-geometry-without-gdal.md) | Пространственный слой без GDAL |
| [ADR-0002](adr/0002-analytics-without-numpy.md) | Аналитика на стандартной библиотеке |
| [ADR-0003](adr/0003-server-side-rendering.md) | Отрисовка страниц на сервере |

**Практическая польза формата.** Необходимость письменно изложить основания
выбора вынуждает рассмотреть отвергнутые варианты по существу, а не
отбросить их по привычке. При работе в одиночку это частично компенсирует
отсутствие обсуждения с коллегами.

Каждая запись содержит раздел «Последствия», включающий и отрицательные:
фиксация недостатков принятого решения не позволяет представить его
беспроигрышным и облегчает пересмотр, если условия изменятся.

## 7. Управление конфигурацией

### 7.1. Ветвление

Применена упрощённая модель: основная ветвь `main` и ветвь разработки
`develop`. Ветви для отдельных функций не создавались — при единственном
исполнителе их назначение (изоляция параллельных работ) не реализуется.

### 7.2. Фиксация изменений

Каждая фиксация соответствует одному завершённому изменению. Сообщения
оформлены по соглашению Conventional Commits: тип, область, краткое описание.

Всего выполнено более семидесяти фиксаций, распределённых по итерациям
пропорционально трудоёмкости.

### 7.3. Непрерывная интеграция

При каждой отправке изменений выполняются: проверка стиля, прогон набора
автотестов на двух СУБД, системные проверки Django и проверка полноты
миграций.

## 8. Итоги

### 8.1. Достижение целей

| Критерий успеха | Пороговое значение | Достигнуто |
|---|---|---|
| Функциональные требования | 14 из 14 | 14 |
| Нефункциональные требования | 8 из 8 | 8 |
| Автотесты пройдены | 100 % | 100 % |
| Покрытие кода | не ниже 80 % | 86 % |
| Открытых дефектов уровня «серьёзный» и выше | 0 | 0 |
| Срок | 8 недель | 8 недель |

### 8.2. Извлечённые уроки

**Заниженная оценка трудоёмкости интерфейса.** Работы по шаблонам оценены в
полтора раза ниже фактической трудоёмкости. Причина — оценка велась по числу
разделов, тогда как трудоёмкость определяется числом различных состояний
интерфейса: пустой результат отбора, недостаток данных для расчёта,
отсутствие полномочий.

**Ценность раннего выполнения работ с высокой неопределённостью.**
Пространственный слой не лежит на критическом пути, но был выполнен первым.
Если бы выбранный подход оказался неработоспособным, изменение решения на
второй неделе потребовало бы переработки одного модуля, а на шестой — всей
модели данных.

**Автотесты как средство обнаружения, а не подтверждения.** Наибольшую пользу
принесли не тесты, подтверждающие ожидаемое поведение, а проверки граничных
случаев: повторное выполнение операции, пустая база, действие пользователя
над собственной учётной записью. Четыре из семи дефектов выявлены именно так.

**Полезность формата ADR при работе в одиночку.** Формат обязывает изложить
основания выбора письменно, что вынуждает рассмотреть отвергнутые варианты по
существу. Раздел «Последствия», включающий отрицательные, не позволяет
представить решение беспроигрышным.

### 8.3. Направления развития

Работы, не вошедшие в объём проекта, но представляющие интерес для
продолжения:

- интеграция с источниками данных в режиме реального времени;
- построение маршрутов с учётом ограничений движения грузового транспорта;
- сопоставление показателей с другими городами;
- уточнение коэффициентов сценарной модели по мере накопления наблюдений;
- архивирование наблюдений старше года для сохранения производительности.
